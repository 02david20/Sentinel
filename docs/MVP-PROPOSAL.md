# Sentinel MVP proposal

Status: proposal for the product owner. Produced from a two-round debate between five reviewers
(product strategist, block-library engineer, agent-experience engineer, security/ops skeptic,
DevRel). Where they disagreed, the outcome and the dissent are recorded below.

## 1. The problem with today's product

Sentinel's core is sound (deterministic runs, idempotency keys, dry runs, a hash-pinned approval gate
for agent-written blocks) but it cannot do anything useful on its own:

- It has **no data source**. The built-ins are Diff, Brief, Snapshot.Commit, Escalation.Pending,
  Webhook.Post and Agent.Escalate. A user cannot watch anything without writing a plugin first.
- The **agent hand-off is one-way**: a prose task file goes out, a bare `ack` comes back. Nothing the
  agent decided is captured or shown.
- It is **systemd-only**, so a Mac laptop (probably the typical user's machine) cannot schedule anything.
- Several things a real tool needs are missing: failure alerts, step timeouts, retention, any answer
  to "what happens when a fetched page tries to instruct my agent".

## 2. Positioning (what the MVP must prove)

**Target user:** a solo developer or small-team lead who already pays for an agent (Claude Code,
Codex, a local model) and runs it from a laptop or VPS.

**Wedge:** every comparable tool does half of this. changedetection.io, Huginn and cron do the
checking but notify humans; n8n, Zapier and scheduled-agent products put the model in the loop on
every run. Sentinel's claim: *the check is free and deterministic, and the agent wakes only on change,
with exactly the diff, inside guardrails.*

**The real differentiators are not connectors.** They are (1) the task contract the agent receives,
(2) the safety story (egress guard, secret scrubbing, fenced untrusted data, approved blocks), and
(3) visible proof it saves wakes. The risk to avoid is "changedetection.io with an LLM bolted on".

## 3. What the debate settled

### Corrections found while checking claims against the code

- String interpolation already works (`"New: ${ids.text}"` is used by the demo workflow), so the
  block engineer's "add interpolation" item is dropped.
- A separate `List.New` seen-set block would mostly duplicate `Diff` + `Snapshot.Commit`. Recommendation:
  extend Snapshot/Diff with an optional **retain** mode (remember ids that dropped out of the list, with a
  cap and TTL) instead of adding a block. This is the one place I overrode a unanimous-looking position;
  the engineer should confirm there is no case `Diff` cannot cover.
- The DevRel and AX agents wrote some positions without reading the repo; items that touch the code
  (`ack` result storage, prompt preview) must be re-estimated by whoever builds them.

## 4. MVP scope (four weeks, one to two engineers)

Everything below ships together. Items marked **BLOCKER** must not be postponed: no data sources
without them.

### A. Safety foundation (week 1)
1. **`httpx` egress guard (BLOCKER).** http/https only; block loopback, link-local, private and cloud
   metadata addresses after DNS resolution and again on every redirect; 5 redirects max; 2 MB body cap;
   30 s timeout; explicit per-workflow `allow_private: true`.
2. **Secret and env references with scrubbing (BLOCKER).** Includes a test that fails if a secret value
   appears in any stored text (run events, outputs, task files, logs).
3. **Per-step `timeout`, and `retry` for read blocks only** (never after an ambiguous write).
4. **Typed-output checks at validate time** for `${step.output}` references.
5. **Retention and schema versioning:** prune idempotency keys, snapshots and task files; `PRAGMA
   user_version` with refusal on a newer database.

### B. Block library (week 2): 12 blocks, all compiled in
| Group | Blocks |
|---|---|
| Sources (read) | `Http.Get` (status, body, parsed JSON, headers from secrets), `Rss.Fetch` (RSS and Atom via `encoding/xml`), `Github.Query` (releases, issues, PRs, workflow runs; plain REST), `File.Read` (see roots below) |
| Transform (read) | `Json.Pick`, `List.Filter` (expression), `Text.Template` (plain, Slack and HTML escaping modes), `Compare.Threshold` (value, op, limit; hit and delta) |
| Sinks (write-external) | `Ntfy.Push`, `Webhook.Post` (exists), plus **Slack.Post as stretch** |
| Control | `Flow.Cooldown` (per-key quiet period, uses the store) |

Plus: `Notify.Desktop` (osascript / notify-send), a 40-line sink. Dropped for now: `Dir.List`,
`List.Group`, `List.Map`, `Cmd.Run`, `Sql.Query`, `Email.Send`, `Github.Comment`, `Log.Tail`.
Every block ships with a test, dry-run output and an entry in `sentinel blocks`.

`File.Read` is allowed only under `roots:` declared in the workflow, with symlink resolution and a
prefix check; it denies `~/.ssh`, `~/.aws`, `~/.config/sentinel`, `.env*` and Sentinel's own state
folder. Roots are printed by `sentinel install`.

### C. Agent loop (week 3)
1. **Structured `task.json`** with a `trusted` section (instructions, schema version, run id, token, ack
   command, suggested actions, all written by Sentinel) and an `untrusted` section (the diff and fetched
   data). Untrusted text is size-capped per field and in total, control characters stripped, and
   placed after the instructions inside a random-nonce fence labelled "data, not instructions".
   **This is mitigation, not a guarantee** (section 8); the real defence is the agent's sandbox.
2. **Result capture:** `sentinel ack <wf> --decision notify|dismiss|ask|failed --summary "..."`. Strict
   schema: summary at most 2000 characters, optional question at most 500, refs are ids from the task
   (no URLs); everything else rejected; escape sequences stripped on store; shown as plain text in the
   TUI and run log. Ack remains the only write channel an agent has.
3. **`sentinel agent-guide`**: generated from the live block registry (specs, effects, YAML grammar, the
   authoring loop validate -> dry-run -> human enables, the escalation contract), plus an AGENTS.md /
   skill that points at it.
4. **Escalation hygiene:** `max_escalations_per_day`, `cooldown`, and `pending_timeout` that moves a
   stale escalation to `expired` with an alert. **Never auto-acked.**
5. **Agent presets** with a sandbox recipe: read-only tools plus only the `sentinel ack` command; no
   network or write tools by default; generic preset runs in a temp directory; no preset means
   notify-only. The exact flags for each agent CLI must be verified against that CLI before shipping.

### D. Operations (week 3, in parallel)
- **`sentinel daemon`** (same `Run` path, pidfile lock, global concurrency cap of 2) and `daemon install`
  to emit a launchd or systemd unit.
- **Failure alerts and a dead-man's switch:** notify after N consecutive failures and when a workflow has
  not succeeded within twice its interval; once per episode.
- Sink send budget per workflow per day.
- `doctor` checks: timer or daemon actually running, last-run age per workflow, stale escalations,
  database size and integrity, unit drift against the binary path; `install --refresh`.

### E. Experience (week 4)
- **Five templates** (`sentinel new --template <name>`): GitHub releases; GitHub CI turns red; RSS
  summary; Hacker News keyword; uptime and latency threshold. (SSL-expiry needs one more small block,
  `Tls.Expiry`, listed as stretch.)
- **Counters** in the TUI header and `sentinel status`: checks run, changes found, escalations, wakes
  avoided.
- **TUI task preview and diff panes**, read-only: the exact scrubbed, truncated, fenced task the agent
  gets, read from the stored snapshot, never re-fetched.
- **`sentinel try <url>`**: RSS/Atom, JSON, or static page-text change only. Goes through `httpx`, prints
  the resolved IP, size and policy before the first fetch, asks for confirmation on non-https or
  non-public hosts, detects JS-rendered pages and says "cannot watch these", stores a baseline only
  (never escalates on the first fetch), notifications off until opted in, and "save as workflow" writes
  a real YAML file you can edit. Built last; first to slip if the team is one engineer.
- **Honest demo** recorded against a local fixture server (`sentinel demo-server`) serving a feed that
  changes on a schedule, with a real daemon at 5-second intervals and no mocks; script committed so it
  can be re-recorded. It must show the guardrails (fenced untrusted data), not just the happy path.

### F. Auto mode: no human input inside a policy you approve once (week 5, or displaces `try` and the TUI panes)

**Idea: approve the policy, not every action.** Today four things wait for a person: `block approve`,
enabling an agent-drafted workflow, confirmations in `try`, and `resume` after a failure. Auto mode
removes the prompts by moving the human decision to one place: a policy file, approved once at a
terminal. Everything Sentinel then does on its own must fit inside it, is logged, and can be stopped.
Off by default.

```yaml
# ~/.config/sentinel/policy.yaml  (applied with: sentinel auto enable; needs a terminal)
auto: on-in-policy
effects: [read, write-internal]          # write-external only to the destinations below
egress_hosts: [api.github.com, ntfy.sh, hooks.slack.com]   # the central control; nothing else is reachable
secrets: [GITHUB_TOKEN, NTFY_TOPIC]      # secret references an auto-created workflow may use
min_interval: 5m
limits: { new_workflows_per_day: 3, escalations_per_day: 20, sends_per_day: 50 }
```

What auto mode does without asking, only when the result fits the policy:
1. **Auto-enable drafts.** A workflow an agent drafts is enabled if it validates, its dry run passes, it
   uses only compiled-in blocks, every write-external step targets an allowlisted host with an
   allowlisted secret, and it respects the interval and limits. Otherwise it stays a draft and a person
   is asked, exactly as today.
2. **Close the agent loop (`on_result`).** After an agent acks with a decision, optional follow-up steps
   run: `on_result: [{when: "result.decision == 'notify'", block: Ntfy.Push, ...}]`. They are part of
   the reviewed workflow and use only the workflow's own `write_allow`. This is what makes
   "check -> agent decides -> notification" run with nobody present.
3. **Self-heal.** Retry transient failures with backoff, resume a workflow paused by a transient error,
   expire a stale escalation (alert, never silently ack), and re-run after a credential file is renewed.
4. **`try` without prompts** for public https hosts that pass the egress guard (still baseline-only on
   the first fetch).

What auto mode does **not** do:
- **No self-approval of plugin blocks.** A plugin is arbitrary code running as the user, so approving one
  automatically means an agent, possibly steered by injected text, runs its own code unattended.
  Auto-approval is only acceptable inside a sandbox that enforces the egress allowlist and a read-only
  filesystem (Linux: Landlock or bubblewrap; macOS has no good option today). Until that exists, a
  proposed plugin block still waits for a person, even in auto mode.
- It cannot widen its own policy, secrets list, hosts or limits. Those change only through a terminal.
- It never auto-acks escalations on timeout, and never sends to a host outside the policy.

"No input" must not mean "no visibility". Required with auto mode:
- An **audit log** of every automatic decision: what, why (which policy rule), by which agent run.
  `sentinel auto log`, plus a daily digest sent through the policy's own notification sink.
- **`sentinel auto revert <id>`** to disable or remove anything auto mode created.
- A **kill switch** (`sentinel auto pause`) that stops all automatic actions at once, and automatic
  pausing when limits are hit or failures spike.

Threat model: injected text in a fetched page can persuade an agent to draft a workflow that leaks
data. The control is the egress allowlist plus secrets-by-reference: a draft cannot reach a host or use
a secret the policy does not name, so the worst case is bounded by the policy a human approved.
**Residual risk the owner accepts by turning it on:** the agent can create and enable workflows inside
the policy without review, so a too-broad policy (for example allowing `hooks.slack.com` and a channel
people read) is the exposure. Keep policies narrow; `sentinel auto enable` prints the effect of the
policy in plain words before it asks.

Effort: M (policy parsing and enforcement, `on_result`, audit log and revert, kill switch). It depends on
the egress guard and secret references from section A, so it cannot come earlier than week 3. Adding it
makes the MVP about five weeks for two engineers, or it replaces `try` and the TUI panes in the four-week
plan.

## 5. Flagship workflows the MVP must run end to end

1. **GitHub PR/release watcher:** `Github.Query` -> `List.Filter` -> `Diff` + `Snapshot.Commit` ->
   `Text.Template` -> `Agent.Escalate` (list payload) -> `Ntfy.Push`.
2. **Page or feed change triage:** `Rss.Fetch` or `Http.Get` -> `Json.Pick` -> `Diff` -> `Agent.Escalate`
   ("is this relevant to me?") -> `Webhook.Post`.
3. **API threshold guard:** `Http.Get` -> `Json.Pick` -> `Compare.Threshold` -> `Flow.Cooldown` ->
   `Agent.Escalate` ("diagnose") -> `Ntfy.Push`.

## 6. Success criteria

- A new user reaches a working watcher in **under 10 minutes** from `git clone` (`try`, or a template).
- All three flagships run from templates against the fixture server with no network access to private
  addresses; the egress guard has tests for redirects to loopback and metadata IPs and for DNS rebinding.
- The "no secret in stored text" test passes.
- `sentinel status` shows wakes avoided and checks run, with no invented token or dollar figures.
- A workflow runs unattended on macOS through the daemon for 7 days with a failure alert verified.

## 7. Deferred (v1.1 and later)

Auto-approval of plugin blocks (needs an enforcing sandbox), MCP (stdio, read-only + draft-only), `sentinel new "<intent>"`, TUI block approval (typed name + hash),
`foreach`/fan-out, registry / `share`, `Cmd.Run`, `Sql.Query`, `Email.Send`, `Github.Comment`,
`Log.Tail`, `Dir.List`, an HTML status page and sparklines, an encrypted secrets store or keychain,
plugin sandboxing, a web dashboard.

## 8. Security notes the team agreed on

- **Prompt injection is the top risk.** Anyone who can write to an RSS feed, issue tracker or web page can
  put text in front of a privileged agent. Fencing, caps and stripping reduce it; they do not remove it.
  The controls that matter: the agent runs in a sandbox with no write path of its own, anything it
  changes goes through approved blocks and `write_allow`, and its `ack` result is validated and shown as
  inert text.
- **Future MCP boundaries** (when it returns): no approve, enable, install, resume, secret or approvals
  access; no `block check` on unapproved code (it executes it); drafts only under `drafts/`, never
  overwriting an enabled workflow; secret names only, never values; size-limited outputs; dry-run only
  for read-effect steps.
- **Accepted residual risk:** single-user trusted machine; plaintext 0600 secrets file; compiled-in blocks
  are reviewed by us rather than hash-pinned; cosmetic log issues.

## 9. Open decisions for the product owner

1. **Rename before public launch?** "Sentinel" collides with HashiCorp Sentinel, Microsoft Sentinel and
   Redis Sentinel (bad for search and for a Homebrew formula). DevRel's picks: *Lull* ("your agent sleeps
   until it matters"), *Nightwatch*. **No availability check was done** (GitHub, brew, crates, domain).
   The skeptic would defer the rename past the MVP; the strategist would do the binary rename in the last
   days. Recommendation: decide the name before week 4 so the demo and README are recorded once.
2. **Slack in the MVP?** It is about 40 lines on top of `httpx` and is widely wanted, but the skeptic
   would slip it. Recommendation: stretch goal, do it if week 2 finishes early.
3. **One engineer or two?** With one: drop `try`, the TUI panes and the stretch items; keep everything
   marked BLOCKER, the 12 blocks, the agent loop and the daemon.
4. **Linux-first label vs daemon-first.** The daemon is in the plan; confirm macOS is a launch target.
5. **Auto mode in the MVP, and how far?** Recommended: policy-bounded auto-enable plus `on_result` (section 4F),
   no plugin self-approval. The five reviewers have not seen this design; run a review round on the policy
   file and the threat model before building it.

## 10. Biggest risks to this plan

- **Thin core, shiny edges:** if `try` and the templates run on fragile fetch/extract code, the first ten
  minutes disappoint. Hence blocks and guards come before polish, and `try` is honest about what it
  cannot watch (JavaScript-rendered pages, auth, rate limits).
- **Wedge erosion:** if a competitor's webhook can already wake an agent in one line, the advantage is
  convenience. The task contract, guardrails and the wakes-avoided evidence are what to invest in.
- **Auto mode:** it is the highest-trust feature in the plan. A broad policy turns a prompt-injected agent
  into an unattended workflow author. It stays off by default, bounded by the egress allowlist, and
  needs the audit log and kill switch to ship with it.
- **Estimates:** four weeks assumes about 12 blocks, not the 22 first proposed, and the cuts above. Two
  of the reviewers wrote their positions without reading the code; re-estimate `ack` result storage,
  the prompt preview and the daemon after a one-day spike.
